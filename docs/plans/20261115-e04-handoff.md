## 3. What already exists to build on (E03, merged)

Backend GET readers (live, response DTOs in `src/http/schemas.py`, mapped by
`src/http/mappers.py`):

| Route (under `/api/cases/{case_id}`) | Use in the inspector |
|---|---|
| `/citations/{citation_id}` | Frozen claim text/signature, relationship, passage and alignment/assessment provenance, capture summary + evidence source; `liveClaimPresent` / `liveClaimId` |
| `/claims/{claim_id}` | Counts, signature, `verificationProvenance`, party positions, one passage per evidence link |
| `/evidence/{evidence_id}` | Source metadata, ordered capture summaries (id, hashes, kind, times, `charLength`, `isCurrent`), related claim references — **no bodies** |
| `/evidence/{evidence_id}/captures/{capture_id}?start=&length=` | Code-point text window (`start` in `[0,totalLength]`, `length` 1..50000), returned `length` + `totalLength` |

DTO fields the UI must use: `effectiveRelation` (policy-resolved: `reported_by |
supports | contradicts | uncertain`) and `relation` (raw stored diagnostic — never
label it as support), `alignmentStatus` (`exact | ambiguous | no_match |
not_provided | source_unavailable`), `quote`, `startChar`, `endChar`, `captureId`,
`citationId`, `diagnosticReason`, `verificationProvenance` (`unknown` =
unproven; never "confirmed"). `snapshotId` is **rejected with 422** until R03.

Frontend today: `frontend/src/pages/tabs/ClaimsTab.tsx` + `EvidenceTab.tsx`,
`frontend/src/pages/CaseIntelligenceCenter.tsx`, `frontend/src/app/routes.tsx`,
`frontend/src/types/backend-models.ts` (already contains the E03 interfaces), and
`frontend/src/services/api.ts`. There are **no client calls or UI** for the four
inspector routes yet, and no deep-link helpers.

## 4. E04 scope (what to build)

1. **API client + types** in `services/api.ts` / `types/backend-models.ts` for the
   four readers (additive; tolerate legacy payloads where fields are absent).
2. **Inspector flow inside the existing tabs** (no new top-level page): from a
   claim, "Inspect evidence" lists its linked sources; selecting one shows the
   captured text with the validated quotation highlighted, plus context.
3. **Code-point-safe highlighting**: slice/highlight with `Array.from(text)` (or
   equivalent) — never raw UTF-16 indices; emoji/CJK and repeated quotations must
   highlight correctly. If the API reports `ambiguous`/`no_match`/
   `source_unavailable`/`not_provided`, show an explanatory state and **no fake
   highlight**.
4. **Metadata panel**: claim text, effective relationship, alignment state,
   evidence/capture ids, title, publisher, original/canonical URL, publication
   time if known, observation/recording times, content hash, extraction scope and
   analysis provenance. Missing values are shown as unknown, never invented. Link
   out only via safe external URLs (`rel="noopener noreferrer"`, no `javascript:`).
5. **Text-window navigation** through the capture route (paging/load-more with
   explicit returned/total lengths), and older capture versions selectable by id.
6. **Frozen citation view**: a `?citation=<id>` deep link (on the existing case
   page) renders frozen claim/passage context even when the live claim/link no
   longer exists, using `liveClaimPresent === false` to explain that the current
   claim is no longer present. Selection must survive reload and back/forward.
7. **Shared deep-link helpers** (one module): build/parse URI-encoded URLs for
   claim, evidence, capture window and citation selectors; every consumer imports
   them instead of hand-building query strings.
8. **Distinct states**: loading, 404 (missing/wrong-case), network error with
   retry, empty, unavailable content/quotation. Keyboard selection works and
   focus moves to the selected inspector heading.
9. **No false signals**: no support/confirmation badges derived from alignment or
   counts; `reported_by` is "as reported by the source", not corroboration;
   `uncertain`/invalid are labelled as such.
